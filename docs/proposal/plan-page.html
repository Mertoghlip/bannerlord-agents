Bannerlord Agents Plan

Several Opus 5.5 agents each command a faction on Bannerlord's campaign map, in war and in diplomacy. Each sees only what its faction can see, and is poked when a player would notice something. The model sets strategy and writes the deterministic tools that carry it out. The study asks where the line between model and code should sit, and which strategist is most feasible for an everyday gamer: a frontier model on a personal subscription, a small model on the gamer's own GPU, or a hybrid of the two.

The course frames machine programming as three pillars, with data underneath all of them [1].

Course connections

The split between the model and deterministic code, and the model's tool writing, both rest on the first two weeks of the course.

Week 2 lecture: constrained stochasticity

The Sep 29 lecture is titled "Current AI News, Geometrically Constrained Stochasticity, and Tour of the State of MP" [61]. Gottschlich's written version argues that "language models are stochastic by mathematical necessity (you can't get convergence without it)". What gets called hallucination is bounded error inside that envelope. He presents Deterministic Intent Folding (DIF) as "a deterministic complement" to language models, applied in three places: pre-model data curation, in-epoch error correction, and inference fidelity, a discriminator-style check on model output [58].

The project builds that complement into a game agent. The strategist stays stochastic, and deterministic structure bounds it at three points:

  • What it may output: constrained decoding plus a check on every order and every tool before anything runs. This mirrors DIF's inference fidelity.
  • What the student learns from: outcome-filtered training data, which mirrors pre-model data curation.
  • What actually moves the armies: deterministic tools, some written by the model itself.

The control-level study measures what each step along that line buys. When a student is unsure, it hands the decision to the teacher or keeps its current orders, much as DIF can decline to answer.

Week 1 reading: The Three Pillars of Machine Programming

Section 3.2, on invention through machine learning:

"However, when it comes to synthesizing programs with significant control structure and that require more discrete reasoning, the techniques from the synthesis community tend to outperform the neural network based techniques." [1]

This is the reason for the split. Patrolling, sheltering and relieving a siege are discrete, control-heavy behavior, so they live in programs: tools that we or the model write. The neural model is kept for the judgment calls between them. Letting the model make every move is the comparison that tests the claim.

Week 1 reading: Challenges and Paths Towards AI for Software Engineering

Section 3.4, on long-horizon code planning:

"The challenge of library learning is to derive a library of useful abstractions from a corpus of programs by abstracting out common reusable features." [59]

It adds that a library "must also prioritize ease of use and maintainability, as well as be robust and adaptable to future extensions". The model's tool library is this problem in a game. Each tool is versioned, reused across pokes and runs, and repaired or retired based on its record. Section 3.2 describes LLMs improving code with tool feedback, such as linter or execution feedback. Here the checker, replay tests and in-game results play that role.

System

The system runs two loops. In the play loop, the game bridge watches each faction the way a player would, and pokes that faction's agent when something matters. Between pokes, deterministic tools from a shared library carry out the agent's orders. The agent can add tools of its own to that library. The training loop builds the local student in phase 2.

Pokes reach an agent when its faction sees or hears something a player would notice, or when a tool asks for new orders. The student inherits the teacher's tool library, so part of the teacher's skill reaches it as code.

  1. Game bridge, a C# mod

    • Vision: a faction sees what its parties and holdings can spot under the game's own spotting rules, plus the notices a ruler gets: war declared, a holding besieged, raided or taken, an army destroyed, a diplomatic offer. A party that drops out of view stays on as a last-seen position with a time.
    • State: the view goes out as a compact text report of about 4–8k tokens, and as JSON for logs and training.
    • Execution: orders map to the game's own party commands, and diplomatic actions to the game's own diplomatic actions. The stock AI pauses only for commanders holding an order. Order and tool status go into the next poke.
    • Primitive moves: move to, enter, leave, engage, besiege, raid, follow and hold. Tools are built from these, and the every-move comparison uses them directly. An agent can order only its own faction's commanders.
    • Run control: a fixed starting save, a 60-day horizon, the player parked far away, and fast-forward on. The game pauses while an agent answers a poke (turn-based mode). Live mode, with no pause, measures whether the agents keep up. The game auto-saves and resumes after a crash.

  2. Pokes

    • An agent is poked when:
      • an enemy army comes into its faction's view, for the first time or after a long absence;
      • the ruler gets a notice or a diplomatic offer;
      • a tool asks for new orders;
      • an order finishes or fails;
      • or a full in-game day passes quietly.
    • Pokes that land close together are merged into one, which lists everything that triggered it.
    • In the every-move comparison, no tools absorb small events, so a sighting near any commander also pokes the agent.

  3. Tool library and behavior language

    • Every order in the main system is a tool. A tool is a small state machine written in a behavior language of states, conditions, actions, settings and poke rules. Conditions use only what the faction can see. Actions are the primitive moves.
    • The bridge runs each tool every in-game hour, deterministically. It makes the moment-to-moment moves and pokes the strategist only when its rules say the plan may need to change.
    • Our nine starting tools are written in the same language the agent uses. That proves the language is expressive before the agent writes anything, and keeps our tools and the agent's directly comparable.
    ToolWhat it doesPokes the strategist when
    defendPatrols around a holding, shelters inside from strong armies, strikes weak ones and breaks weak siegesA large army enters the area, a strong force besieges, or strength drops below the floor
    besiegeMarches on a holding, waits for named allies, then besieges and assaults itA relief army is sighted, or the siege is won or lost
    raidRaids villages in an area and avoids armies above a set ratioA large army spots it, or the area is stripped
    huntChases a named army while it stays in view or was seen recentlyContact is lost, or the target joins a larger force

    The defend tool runs on its own between pokes. It changes state as its area changes, and pokes the strategist only when the plan itself may need to change. The agent sets the ratios and the radius.

    Tools the agent writes

    When no tool fits its plan, the agent writes one. Examples: a feint that raids one border to pull defenders away before a siege elsewhere, a screen that falls back toward a named fortress, or a defense that holds two holdings with one army.

    1. Write. The agent drafts the tool in the behavior language, with a name, a description, settings, and rules for when to poke.
    2. Check. A checker confirms that it uses only allowed actions and visible conditions, that its settings are in range, that every state can be reached and left, and that it has at least one poke rule.
    3. Test. The tool runs on recorded game states from earlier runs, in the way SWE-bench runs a patch against a repository's tests [60]. The agent sees the transitions it made.
    4. Deploy. The tool joins the library, and the agent assigns it to commanders like any other.
    5. Repair or retire. Each tool keeps a record of its pokes and results, which the agent sees in later pokes. It revises tools that underperform and retires tools it no longer uses [59].

    The library persists across pokes and runs, like Voyager's skill library [7]. The agent never runs free code. Everything it writes stays inside a language the bridge can check and run deterministically.

  4. Poke scheduler

    • Keeps a queue of pokes for each faction and sends each agent its poke as it arrives. Agents poked at the same moment run in parallel.
    • Each agent has a time limit. If it misses the limit, its commanders keep their current orders and tools.
    • Orders that arrive together are applied in a fixed faction order, so a run can be replayed.
    • Keeps one log for every agent.

  5. Faction agents

    • One per faction, each with its own stated goal and its own strategist.
    • The prompt holds the goal, the rules, the tool library, the poke's triggers, the faction's view, and any messages from allies.
    • The output is a JSON list of orders, any new or revised tools, any diplomatic actions, and an optional message to allies. In the every-move comparison, orders are primitive moves.
    • Each order is checked: every id exists, the commander belongs to the agent's faction, and each tool setting is in range. After one retry, the commander keeps its current order.
    • Allied channel: one short message per poke to allies, delivered with their next poke and logged. Turning it off is a stretch comparison.
    • The experiments give each faction two goals in turn: aggressive and cautious.

  6. Diplomacy

    • Actions: declare war, propose peace, propose or leave an alliance, and call an ally to war, as far as the game and the pack allow. The pack fixes some pairs of realms as permanently hostile, and the bridge refuses any action it forbids.
    • Pokes: a war declared on the faction, a peace or alliance offer, or an ally's call to war.
    • Between agents: the allied channel also carries structured proposals (offer, accept, reject, counter) as well as free text. Realms on the stock AI answer through the game's own rules.
    • Measured: wars started and ended, alliances made and broken, treaties kept, and how often each goal escalates. LLM nation agents have been seen escalating in wargames [51], so this is watched closely.

  7. Dataset

    • One record per poke: faction, stated goal, control level, triggers, view, orders, tools written, diplomatic actions, message, reasons, latency, tokens and cost.
    • Outcomes are attached later: whether each order succeeded, each faction's change in territory and strength over the next 7 days, and the coalition's result for the run.
    • Train and test sets are split by run, so correlated states from one run never land on both sides.

  8. Distillation and serving

    • One shared student, told its faction and goal in the prompt, at two sizes: one that fits beside the game on an 8 GB card, and one that fits on a 16 GB card. Both are fine-tuned with QLoRA [25] on the laptop GPU while the game is closed.
    • The student inherits the teacher's tool library, so part of the teacher's skill reaches it as code instead of weights. The comparison with a student that has only our tools measures how much.
    • Served at 4 or 8 bits beside the game [26][28], with decoding constrained to valid JSON [32]. Agents poked at the same time share the GPU through batched requests [27][28].
    • Variants: outcome-filtered against unfiltered data, and training with or without the reasons [17]. Stretch: one adapter per faction on a single base model [45][46].

  9. Hybrid strategist

    • The local student answers by default.
    • A poke goes to the subscription model when the student's output fails the checks, when the student is unsure (low token probabilities, or two samples disagree), or when the situation is hard: a new war, a diplomatic offer, a large enemy army at a holding, or a siege of a coalition holding.
    • One allowance per session covers every agent, sized to stay within the subscription's usage limits, so the hardest pending pokes go first [29][30][31].

Research questions

  • RQ1Where should the line between model and code sit? How do outcomes, model calls and reaction time change from our tools, to the model's own tools, to the model making every move?
  • RQ2Can the model write tools that pass the checks and match or beat ours, and does a tool library carry its skill to a smaller model?
  • RQ3Which strategist is most feasible for an everyday gamer: a frontier model on a personal subscription, a small local model, or a hybrid? The comparison weighs quality, pause time, usage limits and hardware.
  • RQ4How many faction agents can one gaming GPU serve beside the game, and at what cost in latency, video memory and frame rate?
  • RQ5Do each faction's stated goals survive distillation, both in how it fights and in its diplomacy?
  • StretchHow much does player-like vision cost against a full view? Do allied messages help? Can opposing agents negotiate peace in the arena?

Protocol

  • Every run starts from the same save, and every condition gets the same stated goals.
  • The main comparisons get 5 runs each: the teacher against the stock AI, and the hybrid against subscription-only and local-only play. Other conditions get at least 3.
  • A coalition run takes about 1 hour. Runs go overnight, unattended, and subscription runs are spread across days to stay within usage limits.
  • Turn-based mode measures decision quality and pause time. Live mode measures whether the agents keep up, which is where every-move play should suffer most.
  • Smaller cards are emulated by holding the student to the video memory each card has left once the game has taken its share. The scaling test runs 1, 2, 3 and 4 student agents and records latency, memory and frame rate, without scoring outcomes.
  • Every poke is logged with its triggers, so model calls, reaction times and pause time come straight from the log.
  • Outside comparison point: in Civilization V, cloud-run open models setting strategy won about as often as the built-in AI, at about $0.86 per game [39].

Hypotheses

  1. With tools, ours or its own, Opus 5.5 beats both the stock AI and its own every-move play, with far fewer model calls. Every-move play loses the most in live mode.
  2. Most tools the model writes pass the checks after at most one repair, and they match or beat ours on the strategies they were written for.
  3. A student given the teacher's tool library keeps more of the teacher's results than the same student with only our tools.
  4. For a gamer with an 8–12 GB card, hybrid gives the best balance of quality, pause time and usage.
  5. Batching keeps answer latency well below the sum of single-agent latencies, up to 4 agents.
  6. One shared student keeps each faction's aggressive and cautious goals distinct, in both its campaigns and its diplomacy.

Analysis reports the mean and spread across runs for the coalition and each faction, with bootstrap intervals, and states plainly how few runs there are.

The everyday gamer's choice

The study ends with a recommendation for a typical player. In Valve's September 2026 survey, about 80% of Steam users have at least 8 GB of video memory and about half have at least 12 GB [44]. Introduction and motivation

0.75 p
  • Hand-written rules run game opponents. State machines, behavior trees and utility AI "have traditionally dominated the control of non-player characters in games" [13]. Bannerlord's campaign AI and diplomacy are of this kind [43].
  • That makes opponents predictable and exploitable [13]. The claim that they also break when content changes, as with mods, needs its own source or should be framed as the author's observation.
  • LLM agents now play hard games well. CICERO reaches human level in Diplomacy [6], LLM agents beat StarCraft II's built-in AI at level 5, "Harder" [9], and Voyager builds its own skills in Minecraft [7].
  • Strategy games have many sides and are fought with words as well as armies. LLM multi-agent systems [49][50] and nation simulations [47][51] exist, but in text-only settings on cloud models.
  • Full and hard games still defeat most models [10][11]. Strong play needs a frontier model in the cloud, and every added faction multiplies the cost and the waiting [29][30].
  • Three design questions follow:
    • How much should the model decide, and how much should deterministic code? The course frames the stochastic model as needing a deterministic complement [58], and the Three Pillars paper notes that control-heavy programs suit synthesis better than neural networks [1].
    • Can the model write that code itself?
    • Which setup can an everyday gamer actually run?
  • The comparison is fair to players: the agents see and act like one. AlphaStar was held to a camera view and an action-rate limit for the same reason [14][57].
  • Gaming PCs can host a small model. About 80% of Steam users have at least 8 GB of video memory, 50% at least 12 GB and 37% at least 16 GB [44]. Quantized small models run locally [25][26][28], and one GPU can serve many requests or adapters at once [27][45][46].
  • Game makers already run small models on the player's PC, for conversation, teammates, everyday character behavior and advice to the player [33–38]. None of them hands a faction's strategy or diplomacy to the model.
  • Machine-programming framing: adaptation [1][4][5], intention [1], invention through tools the model writes [52][7][59], and data [21][22][23]. See the pillar case and course connections.
  • State research questions RQ1 to RQ5 from Experiments, and list the stretch questions in one sentence.
  • Contributions:
    • A multi-agent command harness for Bannerlord with player-like vision, pokes and diplomacy.
    • A behavior language and tool library that the model extends itself.
    • A dataset of a frontier model's campaign and diplomatic decisions for several factions, with outcomes.
    • Three studies: where control should sit; whether the model's tools carry its skill to a small model; and which strategist suits the everyday gamer.

1 p
  • Machine programming, from the course: the three pillars [1]; Gu et al. on tool feedback and library learning [59]; SWE-bench's test-based judging [60]; constrained stochasticity and a deterministic complement [58]. Also autotuning with ATLAS [4] and FFTW [5], Halide's split of what from how [2], and FlashFill as an intention example [3].
  • LLM agents in games: CICERO [6], Voyager [7], Generative Agents [8], StarCraft II [9], CivRealm [10], BALROG [11] and a survey [12]. These run on cloud models, and none measures what deployment costs the game.
  • Multi-agent LLM systems, diplomacy and nation simulations: AutoGen [49] and a survey of LLM multi-agent systems [50]; CICERO's negotiation [6]; Richelieu's self-evolving Diplomacy agents [48]; WarAgent's simulated world wars [47]; escalation by LLM nation agents in wargames [51]. All are text-only or board-game settings on cloud models.
  • Strategy from the model, moves from code: the options framework for temporal abstraction [56]; tool use with ReAct [54] and Toolformer [55]; SwarmBrain, where an LLM sets StarCraft II strategy and a condition-response state machine handles the units [53]; Vox Deorum, which leaves the battles to the built-in AI [39].
  • Models that write their own tools: Code as Policies writes robot control code [52]; Voyager keeps a library of skills it wrote [7]; library learning [59].
  • Human-like limits for fair comparison: AlphaStar played through a camera view with a capped action rate [14][57].
  • Learned game agents: AlphaStar learned from human replays before reinforcement learning [14]. In DAgger, the teacher labels the states the student actually reaches [15].
  • Distilling LLMs and agents: knowledge distillation [16]; Distilling step-by-step [17]; Orca [18]; FireAct [19]; AgentTuning [20]. Outcome filtering with STaR [21] and ReST [22]. The data risk of model collapse [23].
  • Local inference, serving and routing: LoRA [24], QLoRA [25], GPTQ, published as OPTQ [26], llama.cpp [28] and constrained decoding [32]. Serving many requests and adapters on one GPU with vLLM [27], S-LoRA [45] and Punica [46]. Routing with FrugalGPT [29], Hybrid LLM [30] and RouteLLM [31].
  • Closest prior work:
    • SwarmBrain [53] splits an LLM strategist from a fast state machine for one StarCraft II player, on a cloud model. The model does not write the state machine, and there is no distillation.
    • PUBG Ally [37][38] distills a teacher's behavior into a 2B model sized to the video memory PUBG leaves free. It is a single shooter teammate, and no frame-rate, memory or quality numbers are published.
    • Vox Deorum [39] lets an LLM set Civilization V strategy while the built-in AI fights the battles. Cloud-run models win about as often as the built-in AI, at about $0.86 per game. There is no distillation and no local model.
    • AI Influence [42], a Bannerlord mod, uses an LLM for dialogue and for war or peace decisions, with no evaluation. Acknowledge it.
    • NVIDIA ACE projects [33–36] cover conversation, companions, everyday character behavior and advice to the player.
    • Chen et al. [40] measure a game's frame rate while an LLM runs on the same phone chip, with no game agent. Munk et al. [41] fine-tune a 1B model on GPT-4o output to write game content, with no frame-rate measurement.
  • Positioning sentence: prior work splits strategy from moves for a single player in the cloud with hand-built controllers [53][39], or distills a single teammate onto the player's GPU without publishing the cost to the game [37]. This project runs several faction agents that see and act like players and conduct diplomacy. Its agents write their own deterministic tools. It measures where the line between model and code should sit, and which strategist an everyday gamer can run. Keep "to our knowledge".
